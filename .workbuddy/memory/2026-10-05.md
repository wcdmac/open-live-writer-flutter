逐项对照源码核实，报告**整体正确**，仅一处数字有误：
- **修正报告小误**：遗留#14「探测体有界 2MB」实际 `_maxResponseBytes = 16 * 1024 * 1024`（16 MiB，wordpress_rest.dart:92 / xmlrpc_client.dart:40）。边界约束本身存在且正确，仅报道数值错。
- **Section 一「✅ 已修」全部属实**（核对 file:line）：N1（local+guard）、N2（防抖移除；下游 250ms 预览 editor_state.dart:39/49、300ms 字数 post_editor_page.dart:438 确实存在 → 移除决策成立）、N5/N6/N7/N8、遗留#13/#15/#16。
- **N3/N4「⚠️ 部分修复」属实**：idle 超时已加（正确一半），但超时错误路径写法有缺陷（F1）→ 截断 tmp 可能被提升为缓存命中，故 N4 在该路径复活。
- **F1 (P2) 属实且最关键**：media_cache.dart:167-172 `onTimeout: (s){ s.close(); throw ... }` 错误。`Stream.timeout` 的 onTimeout 收到的是 EventSink，throw 会逃逸到 zone（未捕获异步错误），而 `s.close()` 已使流正常结束 → `await for` 走成功路径 → `len>0` 的截断 tmp 被 rename 成有效命中。改 `onTimeout: (s) => s.addError(const HttpException('...'))` 一行即可将错误导入 catch（清理 tmp + rethrow）。此改动同时补完 N3 可靠性与 N4 截断穿透。
- **F2 (P3) 属实**：仅 60s idle 超时，每 chunk 重置；无总超时。上传侧有 5min 总超时（wordpress_rest.dart:827/833、xmlrpc:547），下载侧缺失 → 1字节/59s 滴流永不中止。需加对称总超时（5min）。
- **F3 (P3) 属实**：app_state.dart:249 `error = userFacingError(...)` 在 guard（:259）之前 → 旧账号慢请求失败仍污染新账号 error（无 notify，下次刷新显形）。error 应走「守卫后提交」。
- **F4 (P3) 属实**：守卫通过后 `await catsFuture/tagsFuture/authorsFuture/themeFuture`（:266-269）再到 `notifyListeners`（:274）无二次守卫；等待期切账号可串号（窗口远小于修复前）。彻底修法：`notifyListeners` 前再校验代际。
- **F5 (P3) 属实**：wordpress_rest.dart:148 `utf8.decode(bytes)` 无 `allowMalformed`；2MB(实为16MiB)截断若切在 CJK 多字节中间 → FormatException → 连接流程失败。改 `allowMalformed: true`。
- **F6 (P3 记录) 属实**：N8「取消」仅放弃结果，上传仍跑满 5min、可能留服务端孤儿文件（uploadMedia 无 cancel token，固有局限）。建议注释记录，后续支持 cancel token。
